# 입찰 기술사양 분석 PoC 실습 가이드 (기본편)

## 0. 파일 구성

| 파일 | 역할 | Dify에서 |
|---|---|---|
| 01_입찰공고문.pdf | 발주처 공고 | **입력** |
| 02_기술사양서.pdf | 요구사항 원문 | **입력** |
| 03_자사_제품카탈로그.md | 자사 제품 스펙 | **지식(RAG)** |
| 04_자사_인증_시험_실적.md | 인증·시험·실적 | **지식(RAG)** |

**가장 중요한 구분**: 공고와 사양서는 지식에 넣지 않는다. 입찰 건마다
바뀌는 입력이다. 지식에 상주하는 것은 자사 자료 2건뿐이고, 이건
다음 입찰에도 그대로 쓴다.

시나리오는 가상이다. 발주처, 기업명, 성적서 번호 모두 실습용이다.

## 1. 카페 FAQ 실습과 무엇이 다른가

| | 카페 FAQ | 입찰 분석 |
|---|---|---|
| 질문의 출처 | 사람이 입력 | **문서에서 자동 추출** |
| 검색 횟수 | 질문당 1회 | 요구사항 개수만큼 반복 |
| 지식의 역할 | 답변 그 자체 | 판정의 **근거** |
| 못 찾았을 때 | "문의 주세요" | "확인 필요"로 표시하고 질의서 후보 |

한 문장으로: FAQ는 **답을 꺼내오는 일**이고, 입찰 분석은 **두 문서를
대조해 판정하는 일**이다.

## 2. 워크플로우 구조

```
Start (기술사양서 PDF 업로드)
  ↓
문서 추출기 → 텍스트
  ↓
LLM ① 요구사항 추출 → JSON 배열 [{조항, 항목, 요구조건}, ...]
  ↓
반복(Iteration) ─ 요구사항 개수만큼:
     ├─ Knowledge Retrieval (쿼리 = 항목 + 요구조건)
     └─ LLM ② 대조 판정 → {판정, 자사값, 근거}
  ↓
LLM ③ 취합 → 대응표 + 기술질의서 초안
  ↓
End
```

**반복 노드가 핵심.** 요구사항 13개를 한 번에 검색하면 벡터가 뭉개져
아무것도 못 찾는다. 항목 하나씩 따로 검색해야 한다.

## 3. 지식 설정 권장값

| 설정 | 값 | 이유 |
|---|---|---|
| 청킹 | 부모-자식 | 자식으로 검색, 부모(표 전체)를 LLM에 전달 |
| 인덱싱 | 고품질 | |
| 검색 방식 | 하이브리드 | 모델명(LT-150), 등급(IP66) 같은 정확 매칭 필요 |
| 가중치 | 의미 0.6 / 키워드 0.4 | 숫자·코드 비중 높임 |
| 상위 K | 5 | |
| 점수 임계값 | 0.4 | |

**FAQ와 정반대인 지점**: 카페는 못 찾으면 "문의 주세요"로 끝나지만,
여기서는 근거 없이 "충족" 판정하면 계약 사고가 난다. 임계값을 넉넉히
잡고 "확인 필요"로 빠지게 하는 쪽이 안전하다.

## 5. 심어둔 함정 4개

AI가 이걸 잡아내는지 보면 성능 차이가 드러난다.

**함정 1: 모델 혼동**
카탈로그에 LT-150과 LT-200이 나란히 있다. 공고는 150W급인데 AI가
LT-200 수치(195W, 9.8kg)를 가져오면 오답이다. 재랭크 모델의 효과를
보여주기 좋다.

**함정 2: 선택사양의 연쇄 효과 (가장 어려움)**
3.1 IP66을 맞추려고 선택사양을 쓰면 무게가 7.2 + 1.4 = **8.6kg**이 되어
조항 3.2의 8kg 제한을 넘는다. 두 조항을 동시에 만족하는 조합이 없다.

항목별로 독립 판정하는 구조에서는 절대 못 잡는다. **RAG의 구조적 한계와
사람 검토가 필요한 이유**를 설명하는 데 쓰면 좋다.

**함정 3: 실적 분류**
5.4는 발전소 실적만 센다. 실적표에는 산업 5건, 공공 2건이 더 있어
총 9건이지만 발전 부문은 2건뿐이다. "9건 보유, 충족"이라고 하면 오답.

**함정 4: 시험 항목의 부재 확인**
4.3, 4.4는 "없다"는 것을 판정해야 한다. 검색해서 안 나온 것과, 실제로
없는 것을 구분해야 하는데, 설비 현황표에 "미보유"라고 명시해 두었으므로
제대로 검색하면 근거를 찾을 수 있다. 여기까지 짚으면 잘 되는 것이다.

## 7. 실습 순서

1. **지식 2건 업로드.** 검색 테스트에서 "방수 등급", "발전소 납품실적",
   "염수분무 시험" 세 개를 던져 본다. 세 번째가 특히 볼 만하다.
   청킹 방식에 따라 설비 현황표가 잡히기도 하고 안 잡히기도 한다.
2. **챗봇 앱으로 단순 질의응답부터.** 카페 실습과 같은 구조로
   "LT-150 방수 등급이 뭐야?" 정도를 물어본다.
3. **워크플로우로 전환.** 요구사항 추출 LLM만 먼저 만들어
   JSON이 제대로 나오는지 확인한다.
4. **반복 노드 + 검색 + 판정 추가.**
5. **정답표와 대조해 정확도 측정** (13개 중 몇 개 맞췄는지).
6. 프롬프트 개선 후 재측정.

5번이 실습의 핵심이다. "잘 되네요" 대신 "13개 중 10개 정확"이라고
말할 수 있어야 프롬프트를 고칠 근거가 생긴다.
