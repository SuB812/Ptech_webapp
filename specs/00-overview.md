# 00. 프로젝트 개요

## 1. 목적

발전소 입찰공고와 기술사양서(PDF)를 AI가 분석해 핵심 요구조건을 추출하고,
자사 제품사양·시험자료(RAG 지식베이스)와 대조해 **항목별 판정**을 내린 뒤,
대응표·제출서류 체크리스트·기술질의서 초안을 생성하는 웹 기반 업무 지원 시스템.

입찰 담당자가 수작업으로 며칠 걸리던 "사양서 한 줄씩 읽고 자사 자료 뒤져 대조표 만들기"를
초안 수준까지 자동화하는 것이 목표다. 최종 판단은 사람이 한다.

## 2. 이 단계의 범위 (PoC / 데모)

이번 단계는 **PoC**다. 성공 기준은 기능 개수가 아니라 정확도다.

**완료 기준**
1. 샘플 공고문·기술사양서 PDF 2건을 업로드해 요구사항을 자동 추출한다.
2. 자사 자료 2건이 RAG 지식베이스에 색인되어 있다.
3. 추출된 요구사항을 **항목 하나씩** 검색·판정해 충족 / 보완 필요 / 확인 필요를 근거와 함께 표시한다.
4. `specs/09-acceptance-tests.md` 의 13개 정답표와 대조해 정확도를 숫자로 낼 수 있다.
5. 대응표·체크리스트·기술질의서 초안을 화면에서 확인·수정하고 Excel로 내려받는다.

## 3. 비범위 (만들지 않는 것)

명시적으로 제외한다. 요청이 없는 한 구현하지 않는다.

- 로그인·회원가입·사용자 권한 관리 (PoC는 단일 사용자, 인증 없음)
- 멀티 테넌시, 조직/부서 분리
- 나라장터 등 외부 조달 시스템 연동, 공고 자동 수집
- 알림(이메일/슬랙), 결재 워크플로우, 코멘트·멘션 협업
- 다국어 UI (한국어만)
- 스캔 PDF OCR (텍스트 레이어가 있는 PDF만 대상)
- 원가·견적 계산, 낙찰가 예측
- Celery/Redis 기반 작업 큐, Docker 배포 파이프라인, CI/CD
- 모바일 앱, 반응형 최적화 (데스크톱 1280px 이상 기준)
- 문서 버전 비교(diff), 변경 이력 추적 UI

## 4. 데이터 성격

모든 샘플 데이터는 **가상 데모 데이터**다. 발주처명, 기업명, 시험성적서 번호 모두 실습용이며
민감정보·개인정보는 포함되지 않는다. 따라서 암호화 저장, 접근 감사 로그, 데이터 마스킹은
이번 범위에 넣지 않는다.

단, API 키는 예외다. `.env` 로만 관리하고 `.gitignore` 에 반드시 포함한다.

## 5. 핵심 설계 원칙

이 5개가 이 프로젝트의 정체성이다. 구조를 바꿀 때 이걸 깨면 안 된다.

### 원칙 1 — 입력과 지식은 다른 것이다

| 구분 | 문서 | 수명 |
|---|---|---|
| **입력(Input)** | 입찰공고문, 기술사양서, 구매규격서, RFP | 입찰 건마다 교체 |
| **지식(Knowledge)** | 자사 제품카탈로그, 인증·시험·실적 현황 | 상주, 다음 입찰에도 재사용 |

공고문과 사양서를 지식베이스에 색인하면 다음 입찰 때 이전 건의 요구조건이 근거로 튀어나온다.
**입력 문서는 절대 벡터 색인하지 않는다.**

### 원칙 2 — 항목 하나당 검색 한 번

요구사항 13개를 한 쿼리로 검색하면 벡터가 뭉개져 아무것도 못 찾는다.
추출된 요구사항을 배열로 만들고, 반복(iteration)하며 항목별로 독립 검색·판정한다.

### 원칙 3 — 근거 없으면 "충족"이 아니다

카페 FAQ 챗봇은 못 찾으면 "문의 주세요"로 끝난다. 입찰 분석은 근거 없이 "충족"으로
판정하면 계약 사고가 난다. 근거를 못 찾으면 **"확인 필요"** 로 분류하고
기술질의서 초안 후보로 넘긴다. 임계값은 넉넉히 잡고 `CHECK` 로 빠지게 하는 쪽이 안전하다.

### 원칙 4 — 판정은 3분류, 근거는 위치까지

`충족` / `보완 필요` / `확인 필요`. 각 판정에는 근거 문서명, 절/표 위치, 인용 문장을 붙인다.
사용자가 근거를 클릭해 원문을 확인할 수 있어야 한다.

### 원칙 5 — 검색은 의미 + 키워드 하이브리드

`LT-150`, `IP66`, `HB-T-2024-011`, `KS C 7658` 같은 모델명·등급·성적서 번호는
의미 검색만으로는 정확히 안 잡힌다. 의미 0.6 / 키워드 0.4 가중 하이브리드로 설계한다.

## 6. 원칙만으로 해결되지 않는 한계 (설계에 반영)

원칙 2(항목별 독립 판정)는 **조항 간 상호작용을 구조적으로 못 잡는다.**

예: 조항 3.1(IP66)을 선택사양으로 맞추면 무게가 7.2 + 1.4 = 8.6kg이 되어
조항 3.2(8kg 이하)를 위반한다. 두 조항을 동시에 만족하는 조합이 없다.
항목별로 따로 보면 각각 "선택사양으로 해결 가능"이라는 결론이 나온다.

따라서 항목별 판정이 끝난 뒤 **교차조항 검증(Cross-Clause Check)** 단계를 별도로 둔다
(`specs/06-analysis-pipeline.md` 5단계). 이것은 자동으로 생기는 능력이 아니라
명시적으로 설계한 별도 패스다.

## 7. 용어

| 용어 | 정의 |
|---|---|
| 입찰 건 (BidProject) | 하나의 공고에 대한 분석 단위. 공고문 + 사양서 + 분석 결과를 묶는다 |
| 입력 문서 (SourceDocument) | 분석 대상 PDF. 공고문 또는 기술사양서 |
| 지식 문서 (KnowledgeDocument) | RAG에 색인되는 자사 자료 |
| 요구사항 (Requirement) | 사양서에서 추출한 조항 단위 요구조건. 조항번호 + 항목 + 요구조건 |
| 판정 (Assessment) | 요구사항 1건에 대한 대조 결과. MEET / GAP / CHECK |
| 근거 (Evidence) | 판정을 뒷받침하는 지식 청크. 문서명 + 위치 + 인용문 + 점수 |
| 분석 실행 (AnalysisRun) | 한 번의 전체 파이프라인 실행. 프롬프트/모델/파라미터를 함께 기록 |
| 교차조항 이슈 (CrossClauseIssue) | 두 개 이상 조항이 동시에 만족될 수 없는 상충 |
| 대응표 (Compliance Matrix) | 요구조건-자사값-판정-근거를 한 표로 정리한 제출 문서 |
| 정답표 (Answer Key) | 정확도 측정 기준. `specs/09-acceptance-tests.md` |
