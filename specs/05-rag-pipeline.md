# 05. RAG 파이프라인 — 추출, 청킹, 임베딩, 하이브리드 검색

## 1. 무엇이 지식이고 무엇이 입력인가 (반복 강조)

| | 입력 (SourceDocument) | 지식 (KnowledgeDocument) |
|---|---|---|
| 파일 | `01_입찰공고문.pdf`, `02_기술사양서.pdf` | `03_자사_제품카탈로그.md`, `04_자사_인증_시험_실적.md` |
| 수명 | 입찰 건마다 교체 | 상주, 다음 입찰에 재사용 |
| 벡터 색인 | **하지 않는다** | 한다 |
| 역할 | 질문(요구조건)의 출처 | 판정의 근거 |

카페 FAQ 챗봇과의 차이를 한 문장으로: FAQ는 **답을 꺼내오는 일**이고, 입찰 분석은
**두 문서를 대조해 판정하는 일**이다. 지식은 답이 아니라 근거다.

## 2. PDF 추출 (`documents/services/pdf_extract.py`)

### 2.1 반드시 pdfplumber 표 추출을 쓴다

샘플 `02_기술사양서.pdf` 를 `pdftotext -layout` 으로 추출하면 표의 열이 한 행씩 어긋난다.

실제 출력 (잘못된 결과):
```
2.1       소비전력
2.2       총 광속 (밝기)                          150 W 이하
2.3       광효율                                20,000 lm 이상
2.4       색온도                                140 lm/W 이상
2.5       수명                                 5,700 K
                                             50,000 시간 이상
```
이대로 LLM에 넣으면 `2.2 총 광속 = 150 W 이하` 라는 요구사항이 만들어지고,
그 뒤 모든 판정이 오답이 된다. **레이아웃 기반 텍스트 추출은 이 문서에서 쓸 수 없다.**

`pdfplumber.extract_tables()` 는 같은 파일에서 정확히 읽는다:
```
['조항', '항목', '요구조건']
['2.1', '소비전력', '150 W 이하']
['2.2', '총 광속 (밝기)', '20,000 lm 이상']
...
```

### 2.2 추출 절차

페이지마다:
1. `page.extract_tables()` → `tables[]` 에 2차원 배열로 저장.
2. 표 영역을 제외한 나머지 텍스트 → `text`.
   구현: `page.filter()` 로 표 bbox 안의 문자를 제외한 뒤 `extract_text()`.
   (간단히 하려면 `extract_text()` 전체를 받고, 표 셀 문자열을 라인 단위로 제거해도 된다.)
3. 페이지별로 `DocumentPage` 를 생성.

### 2.3 검증 (추출 직후 실행)

- 표 행의 열 수가 헤더와 다르면 `warnings` 에 추가한다.
- 첫 열이 `\d+\.\d+` 패턴인 표는 조항 표로 보고, 조항번호가 연속(2.1, 2.2, ...)인지 확인한다.
  끊기면 경고.
- 빈 셀이 있으면 경고. 샘플 `4.4 내진동 시험` 의 기준 열은 실제로 값이 밀려 있어
  (`4.3` 행에 `KS C 7658` 이 들어가야 할 수도 있는 모호한 원본) 경고 대상이다.
  **이 경고는 사람이 FR-07 화면에서 확인하도록 남긴다. 자동으로 고치지 않는다.**
- `page_count == 0` 또는 전체 텍스트 길이 < 50자 → `extraction_failed` (스캔 PDF 가능성).
  OCR은 비범위이므로 사유를 명시하고 실패 처리한다.

### 2.4 Markdown 입력 (지식 문서)

자사 자료는 `.md` 다. 헤딩 구조(`#`, `##`, `###`)와 GFM 표를 파싱한다.
- 표는 파이프 구분으로 파싱해 2차원 배열로 만든다.
- `문서번호:` / `개정일:` / `기준일:` 줄에서 `doc_no`, `revision_date` 를 추출한다.

## 3. 부모-자식 청킹 (`knowledge/services/chunker.py`)

정답표 권장값에 따라 **부모-자식(parent-child) 청킹**을 쓴다.
자식으로 검색하고, LLM에는 부모(표 전체)를 전달한다.

### 3.1 왜 부모-자식인가

`방수·방진 등급: IP65` 한 줄만 LLM에 주면, 그것이 LT-150의 값인지 LT-200의 값인지,
표준 사양인지 선택사양인지 알 수 없다. 표 전체를 주면 맥락이 살아난다.
반대로 표 전체를 임베딩하면 벡터가 뭉개져 `염수분무` 같은 좁은 쿼리가 안 잡힌다.
그래서 **검색은 좁게, 전달은 넓게** 한다.

### 3.2 청킹 규칙

**부모 청크 (`is_parent=true`, `embedding=null`)**
- 표 1개 = 부모 1개. `chunk_type="table"`. 표는 절대 쪼개지 않는다.
- 표가 아닌 절(heading 단위) = 부모 1개. `chunk_type="text"`.
  절이 1200 토큰을 넘으면 문단 경계에서 분할하고 `section_path` 에 `(1/2)` 를 붙인다.

**자식 청크 (`is_parent=false`, `embedding` 채움)**
- 표: **행 1개 = 자식 1개**, `chunk_type="table_row"`.
  내용은 `{헤딩} — {열1머리}: {열1값}, {열2머리}: {열2값}` 형태로 자연어화한다.
  예: `LT-150 구조 — 방수·방진 등급: IP65`
  이렇게 하는 이유: `| IP65 |` 같은 셀 조각은 임베딩 품질이 나쁘다. 열 머리말을 붙여
  문장에 가깝게 만들면 `방수 등급이 뭐야` 같은 쿼리와 의미가 붙는다.
- 텍스트 절: 문장 2~3개 단위, 목표 120~250 토큰, 겹침 40 토큰.
- 헤딩은 자식 내용 앞에 항상 붙인다 (`section_path` 를 내용 첫 줄로 프리픽스).

### 3.3 `section_path` 생성

문서 헤딩 경로를 `>` 로 이어 붙인다.
- `한빛조명(주) 제품 카탈로그 > 2. LT-150 사양 > 2.2 구조`
- `한빛조명(주) 인증·시험·실적 현황 > 3. 시험 설비 보유 현황`

화면에 보이는 `Evidence.location` 은 여기서 마지막 1~2단계만 쓴다 (예: `카탈로그 2.2 구조`).

### 3.4 `keywords` 추출 (정규식, LLM 아님)

자식 청크 본문에서 정확 매칭이 필요한 토큰을 뽑아 `keywords` 배열에 넣는다.

| 패턴 | 정규식 | 예 |
|---|---|---|
| 제품 모델 | `LT-\d{3}` | `LT-150`, `LT-200` |
| 보호 등급 | `IP\d{2}` | `IP65`, `IP66` |
| 성적서 번호 | `HB-[A-Z]+-\d{4}-\d{3}` | `HB-T-2024-011` |
| 인증 번호 | `[A-Z]{2,4}-\d{4}-\d{3,4}` | `KSC-2022-1180`, `HE-2023-0471` |
| 규격 번호 | `KS\s?[A-Z]\s?\d{4}`, `ISO\s?\d{4,5}(:\d{4})?` | `KS C 7658`, `ISO 9001:2015` |
| 문서 번호 | `HB-[A-Z]+-\d{4}-\d{2}` | `HB-CAT-2025-02` |
| 단위 수치 | `\d+(\.\d+)?\s?(W|lm|lm/W|K|kg|mm|시간|℃|MΩ|V|년|주|일|대|%)` | `140 W`, `7.2 kg`, `60,000 시간` |

정규식으로 하는 이유: LLM로 키워드를 뽑으면 색인이 느려지고 비결정적이 되며,
재색인마다 결과가 달라져 정확도 측정이 흔들린다.

### 3.5 `model_tags` 부여 — 함정 1 방어

카탈로그에는 LT-150과 LT-200 사양이 나란히 있다. 청킹 시 각 청크가 **어느 모델 절에
속하는지**를 헤딩 경로로 판정해 `model_tags` 에 넣는다.

```
"2. LT-150 사양" 하위 모든 청크          → model_tags = ["LT-150"]
"3. LT-200 사양" 하위 모든 청크          → model_tags = ["LT-200"]
"1. 제품 개요" (둘 다 언급)              → model_tags = ["LT-150","LT-200"]
"4. 공급 조건" (모델 무관)               → model_tags = []   (공통)
인증·시험·실적 문서 "2. 시험성적서 (LT-150)" → model_tags = ["LT-150"]
납품실적표 (품목 열에 모델명)             → 행별로 해당 모델
```

규칙: 헤딩 경로에 `LT-\d{3}` 이 있으면 그 모델. 없으면 본문 `keywords` 의 모델명.
둘 다 없으면 빈 배열 = 공통 (모델 필터에서 제외되지 않음).

### 3.6 샘플 기준 예상 청크 수

정확한 값은 아니지만 자릿수 확인용. 크게 벗어나면 청킹이 잘못된 것이다.

| 문서 | 부모 | 자식 |
|---|---|---|
| 03_자사_제품카탈로그.md | 10~14 | 35~50 |
| 04_자사_인증_시험_실적.md | 12~16 | 45~65 |

## 4. 임베딩 (`knowledge/services/embedder.py`)

- 모델: `text-embedding-3-small`, 차원 1536 (`.env` 의 `EMBEDDING_MODEL`, `EMBEDDING_DIM`).
- **자식 청크만** 임베딩한다. 부모는 `embedding=null`.
- 배치 크기 64, 실패 시 지수 백오프로 3회 재시도.
- 임베딩 대상 텍스트 = `section_path` + `\n` + `content`.
  (헤딩을 포함시키면 `LT-150` 같은 맥락이 벡터에 들어간다.)
- 색인 완료 시 `KnowledgeDocument.embedding_model`, `chunk_count` 를 채우고 `status="indexed"`.
- 모델을 바꾸면 차원이 달라질 수 있다. `EMBEDDING_DIM` 이 기존 컬럼과 다르면
  기동 시 에러로 알린다. 조용히 섞이면 검색이 무의미해진다.

## 5. 하이브리드 검색 (`knowledge/services/retriever.py`)

### 5.1 왜 하이브리드인가

의미 검색만 쓰면 `IP66` 쿼리에 `IP65` 청크가 거의 같은 점수로 올라온다
(벡터 공간에서 두 문자열은 매우 가깝다). `LT-150` 과 `LT-200` 도 마찬가지다.
등급·모델명·성적서 번호는 **한 글자 차이가 판정을 뒤집는다.** 그래서 키워드 매칭을 섞는다.

정답표 권장 가중치: **의미 0.6 / 키워드 0.4.** 숫자·코드 비중을 높인 값이다.

### 5.2 검색 함수 시그니처

```python
def search(query: str, *, top_k=5, threshold=0.4,
           w_semantic=0.6, w_keyword=0.4,
           model_filter: str | None = None,
           doc_kinds: list[str] | None = None) -> list[RetrievalHit]
```

`RetrievalHit`: `chunk`(자식), `parent`(부모), `score`, `semantic_score`, `keyword_score`, `rank`.

### 5.3 단계

**1) 쿼리 전처리**
- 쿼리에서 `keywords` 와 같은 정규식으로 정확 매칭 토큰을 추출 → `query_keywords`.
- 모델명이 쿼리에 있으면 `model_filter` 로 승격한다 (명시 인자가 없을 때).

**2) 의미 검색 — pgvector**
```sql
SELECT id, 1 - (embedding <=> %(qvec)s::vector) AS semantic_score
FROM knowledge_knowledgechunk
WHERE is_parent = false AND embedding IS NOT NULL
ORDER BY embedding <=> %(qvec)s::vector
LIMIT 40;
```
코사인 거리(`<=>`)를 쓰고 `1 - distance` 로 0~1 유사도로 바꾼다. 후보를 40개 넉넉히 뽑는다.

**3) 키워드 검색**
```sql
SELECT id,
  GREATEST(
    similarity(content, %(q)s),                                   -- pg_trgm
    CASE WHEN keywords && %(query_keywords)s::text[] THEN 1.0 ELSE 0 END
  ) AS keyword_score
FROM knowledge_knowledgechunk
WHERE is_parent = false
  AND (content %% %(q)s OR keywords && %(query_keywords)s::text[])
LIMIT 40;
```
`keywords` 배열이 쿼리 토큰과 정확히 겹치면 1.0을 준다. 이것이 `IP66` vs `IP65` 를 가른다.
`pg_trgm` 의 `similarity()` 는 부분 일치를 0~1로 준다.

한국어 형태소 분석은 쓰지 않는다 (PostgreSQL 기본 한국어 FTS가 없고, 형태소 분석기 도입은
비범위). `pg_trgm` + 정규식 키워드 배열로 충분하다 — 우리가 정확히 잡아야 하는 것은
한국어 조사가 아니라 코드·등급·수치다.

**4) 점수 결합 (가중합)**
```python
score = w_semantic * semantic_score + w_keyword * keyword_score
```
한쪽에만 등장한 청크는 없는 쪽 점수를 0으로 본다.

> RRF(Reciprocal Rank Fusion) 대신 가중합을 쓰는 이유: 정답표가 가중치 0.6/0.4를
> 명시하고 있고, 사용자가 화면에서 가중치를 바꿔 효과를 비교하는 것이 데모 목적이다.
> RRF는 가중치의 의미가 직관적으로 드러나지 않는다.

**5) 모델 필터 / 재랭크 — 함정 1 방어**

`model_filter` 가 주어지면:
- `model_tags` 가 빈 배열인 청크: 통과 (공통 정보).
- `model_filter` 를 포함하는 청크: 통과, `score` 에 `+0.1` 보너스.
- 다른 모델만 태그된 청크: `score * 0.3` 으로 **강하게 감점**한다. 완전히 버리지는 않는다
  (사람이 "LT-200 값이 올라왔다"를 볼 수 있어야 하고, 모델 태깅이 틀렸을 여지도 있다).

이 단계가 "LT-150 요구에 LT-200의 195W·9.8kg가 근거로 붙는" 오답을 막는다.

**6) 임계값 및 상위 K**
- `score < threshold`(기본 0.4) 인 청크는 버린다.
- 상위 `top_k`(기본 5)만 남긴다.
- 자식 청크의 부모를 함께 로드한다. 같은 부모의 자식이 여러 건 걸리면 부모는 한 번만 전달한다.
- **결과가 0건이면 빈 리스트를 반환한다.** 임계값을 낮춰 억지로 채우지 않는다.
  0건은 `CHECK` 판정으로 이어져야 하는 정상적인 결과다 (원칙 3).

### 5.4 파라미터 기본값

| 파라미터 | 기본값 | 근거 |
|---|---|---|
| 청킹 | 부모-자식 | 자식으로 검색, 부모(표 전체)를 LLM에 전달 |
| 검색 방식 | 하이브리드 | 모델명·등급 정확 매칭 필요 |
| `w_semantic` | 0.6 | 정답표 권장값 |
| `w_keyword` | 0.4 | 숫자·코드 비중 높임 |
| `top_k` | 5 | 정답표 권장값 |
| `threshold` | 0.4 | 넉넉히 잡고 `CHECK` 로 빠지게 하는 쪽이 안전 |
| 후보 풀 | 40 | 결합 전 각 경로에서 뽑는 수 |
| 모델 불일치 감점 | ×0.3 | 함정 1 방어 |

FAQ 챗봇과 정반대인 지점: 카페는 못 찾으면 "문의 주세요"로 끝난다. 여기서는 근거 없이
"충족" 판정하면 계약 사고가 난다. **임계값을 넉넉히 잡고 `CHECK` 로 빠지게 한다.**

## 6. 검색 테스트 기준 쿼리 (FR-12)

지식 색인이 끝나면 아래 3개를 던져 품질을 확인한다. 화면 기본 예시로 제공한다.

| 쿼리 | 걸려야 하는 근거 | 확인 포인트 |
|---|---|---|
| `방수 등급` | 카탈로그 2.2 (IP65), 2.3 선택사양 (IP66), 성적서 HB-T-2024-012 | 표준값과 선택사양이 함께 나오는가 |
| `발전소 납품실적` | 4.1 발전 부문 표 (2건) | 산업·공공 부문이 섞여 올라오지 않는가 (함정 3) |
| `염수분무 시험` | 3. 시험 설비 보유 현황 (`염수분무 시험기: 미보유`) | **가장 중요.** 청킹 방식에 따라 설비 현황표가 잡히기도 하고 안 잡히기도 한다. 여기가 안 잡히면 함정 4를 통과할 수 없다 |
